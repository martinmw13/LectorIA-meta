# Review 30: resplit keeps the scene whole on a null re-classified part

Source: docs/tasks/30-resplit-null-final.md and architecture review candidate 4
(a part re-classified to `final: null` must not be stored silently; keep the
scene whole and record `{ from, reason: "null-final" }`).

What this change does: after the titles call, if any stored part of a split
scene ends with `emotion.final === null` (a single-part group or a merged-group
re-classify, since `classifyScene` never throws), the scene stays whole:
nothing from the split is stored and one `{ from, reason: "null-final" }` entry
lands in the new `provenance.resplit.reclassify_failures` list. Usage already
tracked stays counted, and `merged_back` entries for that scene are dropped
with the split. The `museFailureReason` sanitizer export and its `$1` fix ride
along.

1. Null-final guard is in the right place (`pipeline/resplit.ts:303-307`).
   What this is: the check runs after both re-classify pools (parts at :257-266
   and merged groups at :294-299), so every stored part is covered.
   If we skip it: a split would again be stored with `final_left`/`final_right:
   null` and no failure entry, the exact silent-null path candidate 4 forbids.
2. Usage stays counted (`pipeline/resplit.ts:260-264,295-299` before `:304`).
   What this is: both pools add `usage.jevRequests`/tokens right after each
   `classifyScene` return, before the guard returns null.
   Test 1 pins it: `jev.requests` is 5 and `meta.requests` is 2 even though the
   scene stays whole (`pipeline/resplit-reasons.test.ts:60-61`).
3. `merged_back` is not polluted (`pipeline/resplit.ts:283,301,308`).
   What this is: merged-group tops collect in `localMerged` and flush to
   `mergedBack` only after the guard passes; a nulled scene contributes
   nothing. The single-group fold-back at :278-281 cannot carry a null: null
   tops never merge (:267-269), so that path only fires on equal non-null tops.
   Both tests assert `merged_back` is `[]`.
4. The regex fix is correct and safe (`pipeline/resplit.ts:109`).
   What this is: the old non-capturing `(?:...)` with a `"$1 [redacted]"`
   replacement dropped the key name (`$1` matched nothing); the new capturing
   group keeps it (`api_key [redacted]`). Verified by running the replacement
   directly. No backtracking risk: flat alternation plus `\s*`, same scope as
   before, case-insensitive as before.
5. `museFailureReason` export is additive (`pipeline/resplit.ts:104`).
   Blast-radius (skill disabled, grepped by hand): the only `runResplit`
   callers are the pipeline and `pipeline/freshness.test.ts`,
   `pipeline/resplit.test.ts`; no other module imports `museFailureReason`,
   and no reader consumes `provenance.resplit` (reader sees only book fields,
   ranges, titles, final vector). The new `reclassify_failures` key is
   output-only; `resplitKeys`/`resplitInputOf` untouched, so step freshness is
   unaffected. Existing resplit tests pass unmodified.
6. Tests are meaningful and use fake values only
   (`pipeline/resplit-reasons.test.ts:1-172`). Test 1: one part re-classifies
   to null, scene ids unchanged, `splits`/`merged_back` empty, one
   `reclassify_failures` entry. Test 2: window, Muse-decision, and null-final
   failures land in their own lists on three scenes. Sanitizer tests use
   `demo-value`, `faketoken1`, `demo-abc`, `demo-pass` (no real key prefixes);
   `check:secrets` passes.
7. Contracts line updated (`docs/contracts/book-data.md:24`): lists
   `reclassify_failures` (part re-classified to null, scene left whole)
   alongside `window_failures` and `muse_failures`. Matches the stored shape.
8. No `data/` changes: diff touches only `BUILT_DURING_HACKATHON.md`,
   `docs/contracts/book-data.md`, `docs/tasks/30-resplit-null-final.md`,
   `pipeline/resplit-reasons.test.ts`, `pipeline/resplit.ts`. No paid API
   calls; all clients are fakes.

Checks: `npm test` (38 files, 353 tests pass), `npm run typecheck` (clean),
`npm run check:secrets` (clean), plus a direct node probe of the redaction
