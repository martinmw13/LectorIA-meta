## Findings

1. **Mix toggle has no visible pressed state** (blocker), `app/globals.css:97-103`, `app/player-controls.tsx:35-43`.
   Problem: the only pressed rule targets `button.chopin[aria-pressed="true"]`. The `Mezclar bandas` button sets `aria-pressed` but gets no visual change, so sighted users cannot tell which mode is on. Screen readers hear the state; sighted users get nothing.
   Fix: extend the accent treatment to the mix button when pressed, e.g. share the rule with a second class or match on `[aria-pressed="true"]`.

2. **A one-track playlist ends the music for good** (should-fix), `core/music-schedule.ts:362-364`.
   Problem: `advancePlaylist` returns `noChange` when the next id equals the current id. With a single-entry playlist the wrap lands on the same track, so nothing switches, the element already ended, and `canSkip` is false, so the button offers no recovery. Validation allows one-track playlists.
   Fix: when the wrap lands on the same id, return a switch to it with `crossfadeSec` (re-cue) instead of `noChange`.

3. **Contracts keeps a stale duplicate Change track section** (should-fix), `docs/contracts.md:161-169`.
   Problem: the older section says Next falls back to "the best track overall" and a null scene "cycles all tracks", while the section above (`:87-102`) correctly says same-style. Both cannot be true, and the code is style-scoped everywhere. The struct literal at `:32` also omits `playlists`.
   Fix: delete the duplicate section and add `playlists` to the manifest literal.

4. **Reader selection transitions have no tests** (should-fix), `app/reader.tsx:194-219, 244-250`.
   Problem: mix-off keeps the playing track's soundtrack and style, style change stores the coverage soundtrack, and the style list hides below two qualifying styles. All three rules live inline in the component. Core has 159 passing tests; the wiring that implements the owner rules has none.
   Fix: pull the mix-off and style-change transitions into small pure helpers beside `music-prefs.ts` with tests for off-with-playing, off-with-nothing-playing, and style-change persistence.

5. **Doubled style-scope comment** (nit), `core/music.ts:226-229`.
   Problem: two "Style scope" comments sit stacked, and the "Reader skip rule" intro above already covers the rest.
   Fix: delete lines 226-227.

6. **Coverage loop written twice** (nit), `core/music.ts:393-407` versus `core/music.ts:347-357`.
   Problem: the best-coverage tie-break by lower id exists in both `pickInitialSoundtrack` and `resolveInitialSelection`. A tie-break edit needs both.
   Fix: extract one best-coverage-in-style helper and call it twice.

7. **Style change during playlist leaves a stale index** (nit), `core/music-schedule.ts:417-445`.
   Problem: `switchStyle` sets a new current id but keeps `state.playlist`, so the saved index points at another track. Unreachable today because the reader blocks style changes while the playlist is on.
   Fix: return `noChange` when `state.playlist` is set, one guard.

8. **README never says empty styles stay hidden** (nit), `public/music/README.md:13`.
   Problem: the committed `piano` style has no tracks, so the selector is hidden today, but nothing tells the drop-in author that is expected.
   Fix: one line that styles without audible tracks stay out of the selector.

## Findings

   Problem: the scheduler returns a switch to the same id, but the reader calls `setCurrentId` with the unchanged id, React bails out, and the track effect keyed on `[started, trackId]` never refires. 3. **Style change can land outside the home it stores** (nit), `core/music.ts:436-443`, `core/music-schedule.ts:433-435`.
   Problem: the home becomes the best-coverage soundtrack, but the track is the best match across the whole style, so the bar can show `de otra banda sonora` right after a style change while the stored home names another soundtrack.
