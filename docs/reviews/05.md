# Review: task 5 contracts and scene reader

Verdict: fix finding 1 first. The reader renders and plays, but slow scrolling never moves the music to the next scene. Findings 2 to 6 should land in the same pass; 7 to 11 are nits.

What this change does: adds the module contracts in `docs/contracts.md`, pure track selection and manifest parsing in `core/music.ts`, the slim reader model in `core/reader.ts`, a server-only Oz loader in `server/books.ts`, and the client reader (`app/reader.tsx`, `app/active-scene.ts`, `app/player.tsx`) with a two-track placeholder manifest in `public/music/`.

## Findings

1. **Slow scroll down never advances the active scene** (blocker), `app/reader.tsx:107-119`, `app/active-scene.ts:10-25`.
   Problem: the observer callback scores only the changed entries. A new scene enters the 5 percent band from below with its top under the reading line, so `pickActiveScene` skips it. Its top then crosses the line with no further callback (intersection status does not change), and when the old scene exits, the old entry is filtered out and the result falls back to current. The next scene is adopted only when its top is already above the line at entry, which is the scroll-up direction plus jumps, not scroll-down.
   Fix: use entries only as a trigger and re-snapshot all sections with live rects on each callback, as the mount path already does. Derive the hit flag from rect versus band in the snapshot mapper.

2. **Pause during a crossfade leaves the incoming element playing** (should-fix), `app/player.tsx:61-80`.
   Problem: `toggle` pauses only the live element. For 1.5 s after a track change the standby element is the audible one, so pressing pause in that window sets state to paused while audio keeps playing.
   Fix: pause both refs in `toggle`, or keep the fading pair in one ref both handlers use.

3. **Volume sits in the track-effect deps and restarts fades** (should-fix), `app/player.tsx:28-59`.
   Problem: every slider tick re-runs the track effect. While paused the early return does not apply (live is paused), so each tick reassigns `standby.src` and flips `liveRef`. Mid-fade it also reassigns the incoming `src`, which reloads that track from zero, and starts a fresh interval.
   Fix: drop `volume` from the deps, read it through a ref inside the fade, and return early when the live element already carries the track `src` regardless of paused state.

4. **Validator accepts NaN vector entries** (should-fix), `core/music.ts:34-37`.
   Problem: `isVector8` checks `typeof` only, and `typeof NaN` is `number`. A NaN entry passes `parseManifest`, then poisons the cosine score and the sort order for that track.
   Fix: require `Number.isFinite` for each of the 8 values, one word in the same check.

5. **Tests skip the behaviors the brief asked about** (should-fix), `core/music.test.ts`, `app/reader.tsx:36-61`.
   Problem: no test covers `nextAlternative` with a null scene, `selectTrack` with an excluded current track, the skip override held until the scene change and then used as current, or reselection when the manifest lands after the first scene. The observer wiring has no test beyond the pure picker.
   Fix: add the three core cases (null scene alternative, excluded current, excluded all) and pull `applyScene` into a pure helper beside `active-scene.ts` with two tests: override as base on scene change, cleared after.

6. **Doc says the reader consumes `scenes.json`, code never reads it** (should-fix), `docs/contracts.md:11-20`, `server/books.ts:9-17`.
   Problem: `loadOzBook` reads `book.json` plus `analysis.json` only, which is fine because analysis carries every scene field, but the contract lists `scenes.json` as an input the reader consumes.
   Fix: name `analysis.json` as the scene source and `scenes.json` as the pipeline intermediate it mirrors, in one sentence.

7. **Tie-break repeats an index scan per comparison** (nit), `core/music.ts:96-99`.
   Problem: the comparator calls `manifest.tracks.indexOf` on each tie. Sort is already stable, so ties follow manifest order without it.
   Fix: delete the tie branch and return the diff.

8. **Two `SceneEmotion` types with different shapes** (nit), `core/music.ts:22-26`, `core/types.ts:78-83`.
   Problem: `core/music.ts` exports `SceneEmotion` as `{ vector, intensity, tempo }` while `core/types.ts` uses the same name for `{ jev, muse_override, final, error }`. Each reads fine alone; importing both invites the wrong one.
   Fix: rename the music one to `SceneSignal` or reuse an inline param type.

9. **Snapshot helper takes a flag it never varies** (nit), `app/reader.tsx:31, 101-106`.
   Problem: `snapshot(hit)` is called once with `true`, and `byId.current` is rebuilt on every render.
   Fix: delete the parameter and build the map with `useMemo` on `scenes`.

10. **Reduced-motion choice never updates** (nit), `app/player.tsx:26`.
    Problem: `matchMedia` runs per render with no listener, so flipping the OS setting mid session keeps the old fade until a rerender for another reason.
    Fix: read it once in state with a change listener, or leave it; the wrongness lasts one session at most.

11. **Track swap mid-fade restarts from partial volumes** (nit), `app/player.tsx:43-56`.
    Problem: the cleanup clears the old interval but leaves the old live element at partial volume, and the new run fades from there while the incoming `src` is replaced. Playback converges, only the fade curve kinks.
    Fix: nothing required once finding 3 lands; note it only if the effect is reworked anyway.

## Round 2

What this change does: the fix pass answers findings 1 to 10, adds manifest v2 with hand-labeled emotions, a pure scheduler with dwell/hysteresis/min-track/hard-cut, same-emotion Next, and a two-element player rewrite with loop crossfades and attribution. The rules all land. Three player/scheduler defects do not.

### Must fix

1. **Reader skip choice reverts on the same scene** (breaks Martin's rule), `core/music-schedule.ts:60-100, 151-166`.
   Problem: `evaluateSwitch` never reads `overrideId`, and `tickScheduler` re-runs it every second. After Change track the override is a dead field: it is set in `requestNext` (`music-schedule.ts:185-186`) and cleared in `promote`, but nothing checks it.
   Case (run against the real scheduler): scene pure tristeza, tracks pure/bland tristeza plus calm; Next moves pure to bland with gap 0.145, then `tickScheduler` at 45 s after the press switches back to pure on the same scene, stale `overrideId: bland` still set. Gaps at or above `hardCutMargin` revert within one second instead. The committed fixture hides this only because its same-emotion gaps sit below `switchMargin`.
   Fix: in `tickScheduler`, when there is no pending scene and `overrideId` is set, return `noChange` without the re-check. Pending promotion still clears the override. Add the missing test: override versus a mid-gap scene holds past `minTrackSec`.
   If we skip it: the Change track button undoes itself, worst on scenes where the reader's pick scores far below best.

2. **Loop fade restarts on every timeupdate for 3 s** (audible stutter, repeated reloads), `app/player.tsx:86, 145-157`.
   Problem: `handleTimeUpdate` arms `loopArmedRef` then calls `requestPlayRef`, whose first lines clear `loopArmedRef` back to null. The old element stays `audibleRef` until the fade finishes, so each later timeupdate re-arms, cancels the fade, reassigns `dst.src` (reload), and restarts the fade.
   Case: any looping track within `crossfadeSec` of its end fires timeupdate about 4 times per second; each one restarts the 3 s loop fade.
   Fix: delete the unconditional clear at line 86 and clear the arm only on a real track change, e.g. guard it with `trackRef.current?.id !== next.id` before the assignment. One line.
   If we skip it: every loop point stutters instead of crossfading.

3. **First press can start the same track twice** (self-crossfade), `app/player.tsx:130-141, 174-184`.
   Problem: first-press `toggle` calls `requestPlay(next, 0)`, then the `[started, trackId]` effect fires on the same track and calls `requestPlay(next, fadeSec)`. When the scheduler already switched pre-press, `fadeSec` can be 3, so the track crossfades into itself on the other element. Even at 0 the `src` is assigned twice.
   Fix: remove the direct `requestPlay` call from the first-press branch and let the effect do the single start. Note in the diff that a pre-press scheduler switch then gives a 3 s fade-in on first press; force 0 there if Martin wants instant start.
   If we skip it: readers who read a while before pressing play hear the track restart into itself.

### Should fix

4. **Config override for weights is silently ignored; loop fades bypass the scheduler fade** (one-config rule), `core/music.ts:79-84`, `app/player.tsx:149-168`.
   Problem: `bhattacharyyaSimilarity` reads `MUSIC_CONFIG.weights` directly, so `rankTracks(scene, m, { weights: custom })` scores with the global weights. Separately, the loop and ended paths hardcode `MUSIC_CONFIG.crossfadeSec` instead of the `fadeSec` prop the scheduler reported, so a custom `crossfadeSec` applies to switches but not loops.
   Fix: pass `config.weights` into the similarity call in `scoreTrack`/`rankTracks`, and read the loop fade length from `fadeSecRef` instead of the global.
   If we skip it: tests and future tuning knobs lie about which values are live.

5. **Pause does not freeze the fade** (wrong element resumes), `app/player.tsx:110-127, 185-189`.
   Problem: pause stops both elements but never cancels or freezes the rAF fade. The tick keeps animating gains and flips `audibleRef` while paused. Resuming mid-fade replays both elements (both levels above 0.02) until the fade converges.
   Fix: skip the level update while `playingRef` is false and let the scheduled tick continue the fade on resume. Two lines.
   If we skip it: a pause-resume inside a 3 s fade briefly plays both elements at once.

6. **Ended non-loop track leaves a stale override** (live once finding 1 lands), `core/music-schedule.ts:196-213`.
   Problem: `noteTrackEnded` correctly updates `currentStartedSec` and excludes the ended id, but keeps the old `overrideId`. Harmless today because nothing reads it; after finding 1 the stale id would wrongly block switches.
   Fix: clear `overrideId`/`overrideSceneId` in `noteTrackEnded` together with finding 1. The pre-manifest `activeId` versus scheduler divergence (`app/reader.tsx:26, 81-85`) converges on manifest load and needs no change.
   If we skip it: fixing 1 without this trades one stuck-override bug for another.

3. First press double start: confirmed, conditional on a scheduler switch before first press setting `fadeSec` to 3 or 1.5. Common case (`fadeSec` 0) still reassigns `src` twice.
