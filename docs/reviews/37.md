# Review 37: one owner for persisted music prefs

Source: docs/tasks/37-music-prefs-owner.md and agent-logs/prompts/37-impl.md.
Diff is `origin/main...HEAD` on branch `music-prefs-owner`. `blast-radius`
is disabled in this workspace, so the caller sweep below was done by hand
with grep.

What this change does: `app/music-prefs.ts` gains `createMusicPrefsStore`,
the single owner of `lectoria.music.v1`. `load` reads storage once and
caches the full object; `update` merges a partial patch over it and writes
the merged object back. `app/reader.tsx` routes all three save sites
(session bridge, volume, mute) through partial updates. The reported bug
is gone: touching volume or mute before the manifest loads, or after its
fetch fails, no longer wipes the stored style and Chopin mode.

1. No full-object write from partial knowledge remains
   (`app/reader.tsx:104-107,211-221`, `app/music-prefs.ts:74-84`).
   What this is: `changeVolume` sends `{ volume }`, `changeMuted` sends
   `{ muted }`, `send` sends `{ style, playlist }`, and each merges over
   the cached full prefs. Grep finds zero `saveMusicPrefs` hits in
   `app/`, `core/`, or `docs/contracts`: the store is the only writer.
   Before the manifest loads (or when its fetch fails) the session is
   null, so `send` returns early and writes nothing, while volume/mute
   updates merge over the loaded style and playlist instead of deriving
   them from a null view. The exact failing case is pinned by the new
   test (`app/music-prefs.test.ts:26-38`).
2. Store caching and update-before-load are sound
   (`app/music-prefs.ts:62-87`, `app/reader.tsx:116,140`).
   What this is: `load` caches after the first read; `update` calls
   `load` first, so an update before the mount effect still merges over
   stored fields rather than defaults. `startSession` receives
   `store.load()`, i.e. the merged value including any early update.
   The one startup case this could change (nothing stored, update first:
   `null` vs `{ style: null, ..., playlist: false }`) behaves the same:
   `resolveInitialSelection` falls back for both
   (`core/music-selection.ts:122-127`) and the Chopin-start check needs
   `playlist === true` (`core/music-session.ts:84`). Only two `load`
   call sites exist, both in the reader, so the cache cannot go stale
   across components.
3. No storage access during render
   (`app/reader.tsx:72`, `app/music-prefs.ts:46-53`).
   What this is: `useRef(createMusicPrefsStore())` evaluates during
   render, but `defaultStorage()` only grabs the `window.localStorage`
   reference; the first `getItem` happens in the mount effect
   (`reader.tsx:116`). Server render returns `undefined` via the
   `typeof window` guard, so hydration still starts from the server
   defaults. State (`volume`, `muted`) is applied after, as before.
4. Guarded storage and validation are unchanged
   (`app/music-prefs.ts:19-44`).
   What this is: `readStored` keeps the old `loadMusicPrefs` checks
   line for line (string style, finite 0-1 volume, boolean muted and
   playlist with the same fallbacks); only the storage source is now a
   parameter. `writeStored` keeps the try/catch, and a throwing store
   still merges in memory (`app/music-prefs.test.ts:76-98`). Old values
   without `playlist` load `false` and round-trip
   (`app/music-prefs.test.ts:100-119`).
5. Tests pin behavior, not implementation
   (`app/music-prefs.test.ts:24-173`).
   What this is: eight tests through an injected fake storage assert
   merged values and the stored JSON: the regression, update-before-load,
   empty-storage defaults, bad JSON, throwing storage, old-value
   round-trip, `loadMusicPrefs` behavior (null with no window, window
   values otherwise), and the volume default. The old
   `saveMusicPrefs`-based tests are replaced, not left behind.
6. Diff scope and docs match.
   `reader.tsx` changes only the prefs lines (import, store ref, three
   save sites, two loads); `app/player.tsx`,
   `app/folio/music-style-control.tsx`, and `core/music-session.ts`
   are untouched, confirmed by the name-only diff. `docs/contracts/player.md`
   and `docs/contracts/music-session.md` describe the one store with
   merging partial updates, matching the code, and the task file
   matches the implementation. The `BUILT_DURING_HACKATHON.md` row
   follows the existing format.
