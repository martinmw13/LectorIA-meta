# Review 46: rain skins + skin owner

Source: docs/tasks/46-rain-skins.md.
Diff is `origin/main...HEAD` (agent-logs excluded).

What this change does: `app/skin.ts` becomes the single runtime owner of
the current skin (five ids, `engraving` default, `lectoria.skin`
persistence, `?skin=` preview that never persists, pre-paint script,
cross-tab sync, `useSkin` in `app/use-skin.ts`). The rain button drops
its inline SVG and renders per-skin art from a new `app/icons-rain.tsx`
registry (engraving, watercolor, ink) through `app/icons.tsx`, with all
motion scoped to `data-art`/`data-anim`/hover in `app/styles/ambience.css`.

1. `app/skin.ts` is the sole writer of `data-skin`
   (`app/skin.ts:37,55,82`, `app/layout.tsx:28`, `app/rain-button.tsx:33-35`).
   What this is: the only `dataset.skin` writes in `app/` are the
   pre-paint `SKIN_SCRIPT`, the `storage`-event handler, and `setSkin`.
   `layout.tsx` only renders the server-side `data-skin` attribute, and
   the rain button never touches the DOM attribute (pinned by
   `app/rain-button.test.ts:55-59`). Grep finds no other writer.
   No difference found.
2. Pre-paint script, persistence, and the `?skin=` override are correct
   (`app/skin.ts:21-37`, `app/skin.test.ts:56-94`).
   What this is: a valid `?skin=` wins for that load and returns before
   any storage read, so it is never written; else a valid stored value;
   else the default. `initialSkin` and `SKIN_SCRIPT` share that order,
   and the test executes the script string for every skin plus garbage
   and denied storage. `setSkin` persists behind try/catch, so denied
   storage still applies the live value.
   No difference found.
3. No hydration mismatch (`app/layout.tsx:28`, `app/use-skin.ts:5-7`,
   `app/rain-button.tsx:31-35`, `app/icons-rain.tsx:26-38`).
   What this is: the server renders `data-skin="engraving"` with
   `suppressHydrationWarning`, and `useSkin` hydrates from the constant
   server snapshot (`DEFAULT_SKIN`) before re-reading the live value
   after mount, so a stored watercolor/ink skin swaps art one render
   later instead of during hydration. The rain defs are module-level
   constants built by a pure function (fixed angles, no random, no
   clock), so server and client markup agree.
   No difference found.
4. The icon fallback chain is sound (`app/icons.tsx:69-82`,
   `app/icons-rain.tsx:272-296`, `app/rain-button.tsx:35,106`).
   What this is: `ICON_SETS[skin] ?? ICON_SETS[DEFAULT_SKIN] ??
   BASE_ICONS`. Skins without rain art (`comic`, `anime-ghibli`) fall
   back to the engraving art, which matches the button's own
   `artSkin` resolution, so both paths render the same SVG. Base icons
   render byte-identical markup for every skin, and no def uses
   `dangerouslySetInnerHTML` (both pinned by `app/icons.test.ts`).
   The fixed `rb-*` def ids exist once per page (one button). One
   dead-nil note: `RAIN_ICONS.engraving ?? {}` can never be null, but
   it costs nothing and keeps the type if a set goes missing.
   No difference found.
5. The rain button keeps its engine, prefs, hit area, focus ring, and
   reduced motion (`app/rain-button.tsx:38-89`,
   `app/styles/ambience.css`, `app/styles/player.css:22-28`).

   No difference found.
