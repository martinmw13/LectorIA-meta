## Muse review, round 1

What this change does: the per-scene resplit worker now catches a rejected
Muse decision ask, a rejected titles call, and titles whose ranges do not
match the plan. Each case keeps the scene whole and records `{ from, reason }`
in `provenance.resplit.muse_failures`. Three new tests cover the three cases.

Must fix: none. The catches wrap exactly the decision ask plus the titles
call and its range check. `classifyScene` never throws on provider failure
(it returns an error object), so the re-classify pools after the titles call
cannot abort the build. `trackMeta` runs only when a result exists; a thrown
call has no tokens to record, and tokens tracked before a later failure stay
counted. Failed scenes push at most one `muse_failures` entry and return
before touching shared outputs; `taken` and `reasons` are locals and are
discarded. The duplicate-id and coverage checks after the pool still throw,
which is correct: those are global invariants, not one scene's answer.
`museFailureReason` stores only the error message (at most 200 chars); HTTP
errors carry status plus a short body excerpt, never headers or keys, so no
secret reaches the file.

Should fix:

1. No test pins spend on a failed scene (pipeline/resplit.ts:223,229).
   What this is: the titles call tracks tokens before the range check, so a
   range mismatch keeps the spent tokens counted.
   Fix: assert in the range-mismatch test that `provenance.resplit.meta`
   counts the decision and titles calls for the failed scene. Small test
   addition, no source change.
   If we skip it: a later refactor could drop the accounting and no test
   would catch it.

Nit:

2. `museFailureReason` repeats the error-to-string pattern used by classify
   (pipeline/resplit.ts:97-100). Four lines next to their only use; not worth
   a shared helper.

Fixed: nothing, no Must items. No source diff.

Verdict: clean
