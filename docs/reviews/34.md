# Review 34: one music-mode cycle behind the style control

Source: docs/tasks/34-music-mode-cycle.md and agent-logs/prompts/34-impl.md
(architecture review 6, candidate 1). Diff is `origin/main...HEAD` on branch
`music-mode-cycle`. `blast-radius` is disabled in this workspace, so the
caller sweep below was done by hand with grep.

What this change does: the style stickers plus the Chopin button now speak
one ordered mode list (`core/music-modes.ts`) and one session intent
(`modeAdvanced`), persisted with a `playlist` pref flag. The control props
shrink from 7 to 3. The one intended behavior change: stickers stay enabled
during Chopin and leave the playlist straight for that style.

1. Chopin-on-Chopin after a reload returns to the wrong style
   (`app/folio/music-style-control.tsx:25-26,52-55`).
   What this is: the control keeps a `lastStyle` ref that only fills while
   a style mode is current. A reload with stored `{ style: "piano",
   playlist: true }` starts in Chopin (`core/music-session.ts:84-91`), so
   the ref is empty and the Chopin button calls `onAdvance` with
   `styles[0]` (orchestral), not the stored piano. The session still owns
   the right answer in `selection.style`.
   Fix: let the session own it, as the task already judges: `modeAdvanced`
   to the playlist id while on the playlist exits to `selection.style`
   (matching `playlistToggled`), and the control always sends
   `onAdvance(playlist.id)`. Then the ref, the render-phase ref write at
   :26, and the `styles[0]` fallback all disappear. Failing case first:
   start in Chopin with stored piano, press Chopin, expect piano.
2. Route-null guard sits after the playlist-exit branch
   (`core/music-session.ts:319-330`; old `styleChanged` guarded at old
   :265 first).
   What this is: `modeAdvanced` checks `routeSceneId === null` only on the
   style-to-style path. Chopin to style with a null route now exits and
   switches under a null signal, where old `styleChanged` did nothing
   (old `playlistToggled` exit did act, keeping the old selection).
   A sticker press is an explicit user choice, so acting looks right, but
   no test pins it either way.
   Fix: add the missing test (Chopin to style with null route) for
   whichever behavior is intended; if no-op is intended, move the guard
   above :322.
3. Stale comment on `switchStyle` (`core/music-schedule.ts:348`).
   What this is: "The reader blocks style changes while a playlist plays"
   is no longer true: stickers stay enabled and the session exits the
   playlist for the target style (`core/music-session.ts:322-328`).
   Fix: one line, e.g. "`modeAdvanced` reaches here only when no playlist
   plays; the guard keeps ...".
4. Mode order, cycle, and 2-state fallback are correct
   (`core/music-modes.ts:25-48`, `core/music-modes.test.ts:1-96`).
   Styles with tracks in manifest order, then Chopin only when the
   playlist exists with tracks. Unknown or null current starts at the
   first (`findIndex` -1, plus one, modulo). One mode returns itself,
   zero modes give null, and `modeAdvanced` guards null, unknown
   (:311), and same-mode (:312). The `styleHasTracks` filter repeated in
   the old reader is gone; the only other use is the definition site in
   `core/music-selection.ts:111,121`.
5. `modeAdvanced` matches the old intents switch for switch
   (`core/music-session.ts:308-336`).
   Style to style repeats `styleChanged` (route guard, `switchStyle`,
   null-switch guard, `selection.style = target`). Style to Chopin
   repeats the `playlistToggled` entry (no route guard, `enterPlaylist`,
   full fade). Chopin to style is one `exitPlaylist` under the target
   selection, one `foldSwitch`, one crossfade, `selection.style = target`,
   and the test pins a single fade (`core/music-session.test.ts:289-298`,
   `fadeSec` 3). The unchecked `switchToId === null` exit (no best match)
   behaves exactly like the old `playlistToggled` exit: playlist cleared,
   target selection kept, no switch. No difference found.
6. Starting in Chopin (fade 0, `currentStartedSec` 0) is a state the old
   code could already reach (`core/music-session.ts:84-91`,
   `core/music-schedule.ts:251-275`).
   `enterPlaylist` on a fresh scheduler cues the first Chopin track with
   crossfade 0, the same as toggling the playlist before the first scene
   entry; only the clock value (0) differs. Later tick, scene entry,
   skip, previous, and track end all run the unchanged playlist-on paths,
   and the player gating is untouched: before the first press, track
   changes only swap `src` (`app/player.tsx:183-201`), and `toggle` is
   the single start path (`app/player.tsx:247-254`). No path plays before
   the first press. Covered by the startup tests
   (`core/music-session.test.ts:99-122`).
7. Persistence is complete (`app/reader.tsx:108-115,222-238`,
   `app/music-prefs.ts:24-30`, `app/music-prefs.test.ts:28-73`).
   Every save site (session bridge, volume, mute) writes `playlist` from
   the session view; the bridge saves on selection or playlist change.
   Missing or bad values load `false`, so old stored prefs load. Nothing
   saves before prefs load: the prefs effect runs before the manifest
   fetch resolves, and `send` returns early without a session or
   manifest. `startSession` falls back to the stored style when the
   playlist is missing.
8. The player keeps loop-off and drops Chopin knowledge
   (`app/player.tsx:7,27-31,212,239,386`).
   `playlistOn` still arrives and only drives the two loop-off branches.
   Nothing in the reader or player names the playlist split for the
   control anymore; `findChopinPlaylist` stays re-exported from
   `core/music-session.ts:28` for the session view builder. Grep finds no
   remaining `controlsDisabled`, `playlistLabel`, `onTogglePlaylist`,
   `changeStyle`, or `togglePlaylist` outside tests and logs.
9. Visuals preserved, contracts match, no banned copy.
   Same `stickers`/`sticker`/`sticker-dot`/`chopin` classes, same images
   (the sticker mapping moved to id plus label with identical outputs),
   same aria labels, titles, and `aria-pressed` meaning; the only visual

   `docs/contracts/playlist-mode.md:11-15`). The stale
   `app/player-controls.tsx` line is fixed (`docs/contracts/player.md:48-50`),
   and `music-session.md:5-20` plus `selection.md:11` match the code. Grep
   finds no "Generated" in UI copy or docs.
